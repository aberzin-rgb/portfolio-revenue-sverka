# Сверка выручки по портфелю проектов

## Что это и зачем

Инструмент сравнивает факт выручки за полугодие по каждому проекту одного направления
(например, VK Workspace) из трёх источников, которые ведутся разными людьми и должны
совпадать, но на практике расходятся:

1. **Сводный отчёт по портфелю** — агрегированная таблица, которую проектный офис
   собирает вручную по всем направлениям.
2. **Паспорт проекта** — индивидуальный файл каждого проекта, который ведёт РП; должен
   быть первоисточником для Сводного.
3. **Выгрузка выручки из бухгалтерии** — факт по данным 1С/МСФО, не зависит от людей.

Результат — Excel-отчёт с построчным сравнением и статусом (OK / расхождение / не найдено),
плюс детализация по видам выручки и список "осиротевших" кодов в бухгалтерии, которых нет
в портфеле.

Контекст создания: см. этот же чат-диалог, в котором инструмент был написан и отлажен
на реальных данных VK Workspace, H1 2026. Полную предысторию решений (допуски, что считать
дубликатом, что исключать) искать там же — здесь только рабочая механика.

## Файлы в этой папке

- `sverka.py` — основной скрипт, точка входа.
- `xlsx_min.py` — свой мини-читатель/writer `.xlsx` на чистой стандартной библиотеке
  Python (`zipfile` + `xml.etree`). **Почему не openpyxl:** в среде выполнения нет доступа
  в интернет для `pip install` (см. proxy 403 на pypi.org при проверке) — не пытайся
  ставить openpyxl или другие пакеты, сразу используй/расширяй `xlsx_min.py`.
- `config.json` — все параметры запуска (пути к файлам, год, период, направление,
  допуски). Меняется без правки кода.
- `config_finops.json` — тот же набор параметров, но для направления «FinOps»
  (ЦФО `FINO`/`FINB`) — пример того, как держать несколько направлений параллельно
  (по одному config-файлу на направление, каждый со своим `output_file`).
- `config_finops_year.json` — FinOps, но `"period": "year"` и выгрузка бухгалтерии
  другого формата (`"revenue_format": "journal"`, файл `FinOps 7 мес 2026.xlsx`
  рядом со скриптом) — пример того, как сверять полный год против частично-годовой
  выгрузки, см. "Период сверки" ниже.
- `config_all_h1.json` — `"direction": null` и `"orphan_code_prefixes": null` —
  сквозная сверка **по всем направлениям сразу** (весь портфель), см. "Сверка по
  всем направлениям" ниже.
- `config_workspace_7mes.json` — VK Workspace, тот же приём, что и в
  `config_finops_year.json`: `"period": "year"` + `"revenue_format": "journal"`
  против выгрузки за 7 месяцев (`Берзин 01-07.26.xlsx` рядом со скриптом).
- `config_mikhalsky_h1.json`/`config_mikhalsky_7mes.json`,
  `config_mukhin_h1.json`/`config_mukhin_7mes.json`,
  `config_khabibullina_h1.json`/`config_khabibullina_7mes.json`,
  `config_yablontsev_h1.json`/`config_yablontsev_7mes.json` — сверка не по
  «Направлению», а по `code_prefixes` (ЦФО-коду конкретного руководителя

- `Сверка_VK_Workspace_H1_2026.xlsx`, `Сверка_FinOps_H1_2026.xlsx`,

  `Сверка_VK_Workspace_7мес_2026.xlsx`, `Сверка_Михальский_H1_2026.xlsx`,
  `Сверка_Михальский_7мес_2026.xlsx`, `Сверка_Мухин_H1_2026.xlsx`,
  `Сверка_Мухин_7мес_2026.xlsx`, `Сверка_Хабибуллина_H1_2026.xlsx`,
  `Сверка_Хабибуллина_7мес_2026.xlsx`, `Сверка_Яблонцев_H1_2026.xlsx`,
  `Сверка_Яблонцев_7мес_2026.xlsx` — сгенерированные отчёты (перезаписываются

**Внимание при обновлении данных:** бухгалтерия периодически переносит файл
сводной H1-выручки (`2026 Итого выручка - МСФО факт Н1 v3.xlsx`) в новую папку —
27.08.2026 он переехал из `Отчеты БС OnPrem/По Выручке/` в подпапку
`Отчеты БС OnPrem/По Выручке/Сверка 06_07_2026/` (там же лежат персональные
7-месячные journal-выгрузки по каждому РП). Если скрипт вдруг не находит
`revenue_file` по старому пути — искать файл заново (`find`/по имени), не
предполагать, что структура папок стабильна.

## Как запускать

```bash
python3 sverka.py                    # использует config.json рядом со скриптом
python3 sverka.py --config other.json  # или другой конфиг
```

Скрипт печатает прогресс и статистику по шагам, в конце — список предупреждений
(например, коллизии кодов между несколькими паспортами) и путь к готовому файлу.

## Как переиспользовать под другое полугодие/год/направление

Всё делается правкой `config.json`, код трогать не нужно:

| Поле | Что значит |
|---|---|
| `disk_root` | Корень примонтированного диска Disk-O (см. ниже про сам диск) |
| `summary_file`, `summary_sheet` | Путь к файлу Сводного отчёта и имя листа года (например `"2026"`) |
| `revenue_file`, `revenue_sheet` | Путь к выгрузке из бухгалтерии и имя листа |
| `revenue_format` | `"pivot"` (по умолчанию, если поле отсутствует — обратная совместимость со старыми конфигами) или `"journal"` — см. "Форматы выгрузки бухгалтерии" ниже |
| `direction` | Значение колонки "Направление" в Сводном, по которому фильтруются строки (например `"VK Workspace"`) |
| `code_prefixes` | Альтернатива/дополнение к `direction` — фильтр Сводного по префиксу нормализованного кода проекта (например `["DVPO"]`), см. "Сверка по РП/ЦФО-коду" ниже |
| `year` | Год — используется, чтобы найти правильный блок и в Сводном, и в паспорте |
| `period` | `"h1"` / `"h2"` / `"year"` — какой период сравнивать, см. "Период сверки" ниже |
| `match_tolerance_rub`, `match_tolerance_pct` | Допуск на расхождение — совпадением считается разница ≤ большего из двух |
| `orphan_code_prefixes` | Префиксы ЦФО-кодов (после нормализации), по которым ищутся "осиротевшие" коды в бухгалтерии, отсутствующие в портфеле |
| `output_file` | Имя итогового xlsx |

`summary_file`, `revenue_file`, `pm_folders_root` по умолчанию считаются относительно
`disk_root` — но если указать **абсолютный путь** (например, файл лежит рядом со
скриптом, а не на диске Disk-O — как `FinOps 7 мес 2026.xlsx`), он используется как
есть (`resolve_path()` в `sverka.py`).

Диск примонтирован через приложение **Disk-O** (не физический диск) по пути
`~/Library/Containers/Mail.Ru.DiskO.as/Data/Disk-O.as.mounts/a.berzin@vk.team-mailru`.
Если скрипт не находит файлы — сначала проверь, что диск виден в Finder/примонтирован
(`mount | grep DiskO`), прежде чем менять пути в конфиге.

## Период сверки (`period`: h1 / h2 / year)

Сводный отчёт хранит **четыре одинаковых по составу блока** колонок подряд на одном
листе: H1, H2, "весь год" (метка в файле — `"ПО ВСЕМУ {год}г году"`) и весь срок
проекта (последний блок не используется). `config['period']` выбирает, в каком из
первых трёх искать «Прогноз»/«Факт» — см. `PERIOD_LABEL_TEMPLATES` в `sverka.py`.
Раньше это было жёстко зашито на первый блок (H1) — если увидишь в старом коде, что
"Прогноз" ищется как "первый попавшийся после кода проекта", это тот самый баг.

В паспорте (лист "4. Факт БДР") при `period="year"` берётся **сама строка года**
(например строка "2026"), а не под-строка "1е полугодие"/"2е полугодие" под ней —
у строки года тоже есть свои Прогнозные/Фактические Доходы, это факт с начала года
по настоящий момент (см. `read_passport_h1_actual()`, `half_label=None`).

Когда использовать `period="year"`: когда бухгалтерия прислала выгрузку не строго за
H1/H2, а за произвольный период с начала года (например 7 месяцев) — сравнивать её
нужно с накопленным фактом за год (какой он есть на данный момент), а не с H1/H2
по отдельности, иначе часть выручки (например июльская) не с чем будет сравнить.
См. `config_finops_year.json`.

## Форматы выгрузки бухгалтерии (`revenue_format`)

Бухгалтерия присылает выгрузки в разных форматах от раза к разу — видел уже два:

- **`"pivot"`** (изначальный формат, `parse_revenue_extract_pivot()`) — сводная
  Excel-таблица (обычно лист "Свод в разрезе проектов") со "схлопнутыми" повторами:
  Код проекта/Проект/Вид выручки заполнены только в первой строке своей группы,
  сумма по коду — отдельная строка `"‹КОД› Итог"`, колонка "Общий итог".
- **`"journal"`** (`parse_revenue_extract_journal()`, добавлен для файла
  `FinOps 7 мес 2026.xlsx`) — построчный журнал проводок 1С: каждая строка уже сама
  по себе одна транзакция, все поля (Код проекта, Проект, Вид выручки, Номер/Дата
  договора) заполнены в каждой строке, суммируется скриптом самостоятельно (готовых
  "Итог"-строк нет). Сумма берётся из колонки
  **"Сумма без НДС с плюсом (для бизнеса)"** — проверено, что она равна колонке
  "Сумма без НДС" с обратным знаком (та отрицательная для доходных проводок) —
  то есть тот же факт выручки, просто уже в удобном положительном виде для отчётности;
  колонки "Сумма" и "Сумма без НДС" сами по себе не согласованы друг с другом по
  знаку/итогу и для сверки не подходят.

  **"Вид выручки" — с подвохом.** В этой выгрузке ДВЕ колонки с классификацией вида
  выручки, и они не эквивалентны: "Бюджетный классификатор.Группа статей.Наименование"
  заполнена только примерно в 18% строк, а колонка с (бессмысленным на вид) заголовком
  **"Middle"** — заполнена во всех строках и несёт ту же классификацию, просто полнее
  (включая деление на "...-отложенная выручка VK Tech", без которого столбец «Сумма
  отложенной выручки» на листе «Сверка» занижался в разы). Пользователь поймал это
  руками, сверив с колонкой AS в самом файле. Из-за этого `col_vid` в
  `parse_revenue_extract_journal()` выбирается не по конкретному имени колонки, а по
  тому, какой из кандидатов (["Middle", "Группа статей", ...]) реально заполнен
  чаще на реальных данных — при добавлении нового файла в этом формате проверь
  warning "для 'Вид выручки' среди кандидатов ... выбрана ..." в выводе скрипта,
  что выбор снова корректный.

  Период у journal-файла не фильтруется скриптом — берётся весь период, что есть в
  файле (для 7-месячного файла это Январь-Июль). Если пришлют выгрузку за другой
  период в этом же формате — просто поменяй `revenue_file` и, если нужно, `period`.

Если придёт третий формат — добавляй `parse_revenue_extract_<name>()` по аналогии
и новую ветку в диспетчере `parse_revenue_extract()`, не переписывай существующие
парсеры под новый формат.

## Сверка по всем направлениям сразу (`direction: null`)

`config['direction'] = null` (или `""`/`"*"`) — не фильтровать Сводный по колонке
"Направление" вообще, взять все строки с непустым "Проекты". Так же нужно поставить
`config['orphan_code_prefixes'] = null` — иначе "осиротевшие" коды будут искаться
только среди указанных префиксов, а не по всему файлу. См. `config_all_h1.json`
(добавлен по запросу пользователя — "сплошная сверка за H1 по всем направлениям").

На листе "Сверка" в этом режиме появляется колонка **"Направление"** (берётся из той
же колонки Сводного, что и фильтр в обычном режиме) — без неё в общем списке из
сотни строк непонятно, к какому направлению относится каждая. Колонка полезна и не
мешает в обычном режиме (по одному направлению) — она там просто константная.

## Сверка по РП/ЦФО-коду (`code_prefixes`)

Не все сверки укладываются в фильтр по колонке "Направление" — иногда бухгалтерия
присылает выгрузку не по направлению, а по конкретному руководителю направлений
(ФИО в имени файла, например `Михальский 01-07.26.xlsx`), и его ЦФО-коды могут быть
размазаны по нескольким разным значениям "Направление" в Сводном одновременно
(так, DVPO встречается и в строках с "Направление"="VK Cloud", и в строках с
"VK Cloud (DP)" — вперемешку, судя по всему из-за неаккуратного заполнения этой
колонки людьми). Фильтр по тексту направления в таком случае даёт неполную/неверную
выборку.

Решение — `config['code_prefixes'] = [...]`: фильтрует строки Сводного не по
"Направление", а по префиксу нормализованного кода проекта (та же логика, что уже
была у `orphan_code_prefixes` для поиска осиротевших кодов). Обычно используется
вместе с `"direction": null` (фильтр по направлению отключён полностью, фильтрует
только код) и с тем же списком префиксов в `orphan_code_prefixes`.

Чтобы узнать, какие префиксы кода соответствуют конкретному человеку — открыть его
файл выгрузки (`journal`-формат) и посмотреть уникальные значения колонки
"Код ЦФО". Примеры (H1 2026): Михальский → `DVPO`, Мухин → `S3OO/DTAO/S3OG/DTAG/
S3HG/DTHG/AIPL` (сразу два "Направления" Сводного — Data Services и Data Services
(S3)), Хабибуллина → `MRCO`, Яблонцев → `GVCL`. См.
`config_mikhalsky_h1.json`/`config_mikhalsky_7mes.json` и аналогичные пары для
остальных трёх — `_h1` использует общий сводный pivot-файл выручки (полугодие),
`_7mes` — персональную journal-выгрузку конкретного человека за 7 месяцев (та же
техника "period=year против частичного года", что и в `config_finops_year.json`).

**Важные оговорки для режима "все направления":**
- В листе Сводного, помимо основной таблицы, есть несколько **мусорных строк** —
  похоже на остатки другой мини-таблицы/легенды где-то на том же листе (Проект
  вида "Директоры проектов"/"Рук.группы", Направление — имя человека, Код проекта —
  буквально текст "Код проекта"). В обычном режиме (фильтр по конкретному
  направлению) они никогда не попадали в выборку и были незаметны. Сейчас они
  проходят в отчёт, но безвредны: у них факт = 0, паспорта/бухгалтерии не находится,
  статус "НЕТ КОДА"/"НЕ НАЙДЕНО НИГДЕ" — искажений в цифрах не дают, просто пара
  лишних строк для игнорирования глазами. Не стал городить эвристику под фильтрацию
  именно этих строк — слишком легко случайно отфильтровать так и настоящий проект,
  если совпадёт название.
- Список "осиротевших кодов" без фильтра по префиксу гораздо длиннее и шумнее
  (сотня с лишним кодов). Среди них попадаются коды с ОГРОМНЫМИ суммами (сотни
  миллионов/миллиарды, суффикс вида `_001`) — это, скорее всего, не забытые
  отдельные проекты, а **общие/накопительные коды на уровне всего ЦФО** (когда
  бухгалтерская проводка не привязана к конкретному проекту). Не воспринимай верх
  списка по сумме буквально как "забытые проекты" — сначала проверь, не похож ли
  код на общий/технический бакет, прежде чем идти разбираться к РП.

## Структура результата (3 листа)

1. **Сверка** — по одной строке на проект (или на группу проектов с одинаковым кодом):
   Проект, Направление, Код, РП, Статус проекта, факт по всем трём источникам, пять
   справочных колонок (см. ниже), дельты, итоговый статус сверки, комментарий.
   У каждого заголовка колонки — комментарий Excel (жёлтый уголок) с точным указанием
   файла/листа/ячейки-источника;
   см. `build_main_header_comments()` в `sverka.py`, если нужно поменять текст.

   Справочные колонки рядом с «Факт H1: Сводный» (по просьбе пользователя) — разбивка
   строк «Детали выручки» по коду на 5 непересекающихся корзин (см.
   `categorize_revenue_breakdown()`), сумма которых **всегда равна** «Факт {период}:
   Бухгалтерия» для этого кода (проверено на примерах PLTO-052, PLTO-035, PLTO-050):
   - **Сумма Вычетов (Сводный)** — не из бухгалтерии, а из Сводного: сумма строк
     с ДП='Вычет' по этому коду, **со знаком минус** (те самые корректировки, что
     исключены из основного факта — `group_summary()` не просто выбрасывает их, а
     сохраняет сумму в `vychet_sum` для показа).
   - **Сумма отложенной выручки (Бухгалтерия)** — "чистая" отложенная выручка: строки,
     где в «Вид выручки» встречается «отложенная выручка», **кроме** отложенной по
     лицензиям и СТП (та теперь в двух следующих колонках — иначе она размывала
     реальную причину расхождения). Например: «Выручка от сервисных услуг-отложенная
     выручка VK Tech», «...премиальной технической поддержки-отложенная...»,
     «...подписочных сервисов-отложенная...», «...продажи ПАК-отложенная...»,
     «Технологии для бизнеса-отложенная выручка».
   - **Выручка от лицензий** — строки, где встречается «передачи лицензий» (все 4
     варианта: обычная / отложенная / конс.продажи / конс.продажи-отложенная).
     Диагностика причины расхождения №1: лицензионная выручка иногда проводится не
     на тот код/ЦФО — такая выручка подлежит корректировке бухгалтерией.
   - **Выручка от СТП** — строки, где встречается «стандартной технической поддержки»
     (все 4 варианта). Диагностика причины №2: пересорт между видами ТП или между ТП
     и сервисными услугами — на наших ЦФО стандартной ТП в принципе быть не должно.
   - **Прочее** — остаток: не отложенная (в узком смысле выше), не лицензии, не СТП.
     Сюда попадает и обычная (не отложенная) выручка по премиальной ТП/сервисным
     услугам/подписке/ПАК, и любой вид выручки вне этого списка вообще. Введена как
     диагностика по просьбе пользователя ("посмотрим, сколько там наберётся") — не
     обязательно проблема, entries here просто ещё не разобраны по категориям.

   Все пять — справочные, в дельты (Δ Сводный-Паспорт / Δ Сводный-Бухгалтерия) не
   подмешиваются. Категории проверяются по порядку лицензии → СТП → отложенная →
   прочее (`LICENSE_MARKER`/`STP_MARKER`/`DEFERRED_REVENUE_MARKER` в `sverka.py`) —
   лицензии и СТП «перехватывают» свои отложенные варианты раньше общей проверки на
   «отложенная выручка».
2. **Детали выручки** — построчная детализация из бухгалтерской выгрузки (вид выручки,
   номер и дата договора, сумма) по каждому коду, попавшему в сверку.
3. **Осиротевшие коды** — коды из бухгалтерии с префиксом из `orphan_code_prefixes`,
   которых нет в Сводном отчёте по этому направлению. Часто там реальные деньги —
   стоит смотреть, не забыт ли проект в портфеле. Лист детализирован построчно
   (Код, Итого по коду, Проект/Клиент, Вид выручки, Номер договора, Дата договора,
   Сумма по строке) — так же подробно, как "Детали выручки", просто без фильтра
   по кодам из сверки.

## Ключевые нюансы логики (важно перед доработкой)

Это всё — результат отладки на реальных, довольно "грязных" данных. Если будешь менять
логику, держи в голове эти находки, иначе легко наступить на те же грабли снова:

- **Коды проектов пишут непоследовательно** — `MFB0-030` (цифра 0) и `MFBO-072` (буква O)
  и `MFBO_033` (подчёркивание вместо дефиса) встречаются одновременно. `normalize_code()`
  приводит всё к единому виду (верхний регистр, единый разделитель, 0→O **только в
  буквенном префиксе**, не в числовом хвосте кода).
- **Один код может относиться к нескольким строкам-проектам** в Сводном (например два
  контракта с одним клиентом под одним кодом). `group_summary()` суммирует их факт для
  сравнения с одной цифрой из бухгалтерии.
- **Строки с ДП='Вычет'** — это корректировки к соседней строке, а не отдельные проекты;
  исключаются из сверки (см. `group_summary`).
- **Паспорт нельзя искать по имени файла** — имена не соответствуют названию проекта
  и есть много версий/копий (`rev_01`, `v2`, копии в "Архив"). Единственный надёжный
  способ — открыть файл и прочитать саму ячейку "Код проекта" (лист
  "3. Договоры_Этапы_Доходы"), см. `read_passport_code()`.
- **Названия папок РП не стандартизированы**: "Действующие проекты" у одних, "Текущие
  проекты" у других; "Завершенные проекты" vs "Закрытые проекты". Папки распознаются по
  ключевым словам-подстрокам (`ACTIVE_KEYWORDS`, `COMPLETED_KEYWORDS` в `sverka.py`),
  не по точному имени.
- **macOS отдаёт имена файлов в Unicode NFD**, а строковые константы в коде обычно
  NFC — буква "й" (составной символ) не совпадает при обычном сравнении подстрок без
  `unicodedata.normalize("NFC", ...)`. Уже исправлено в `_folder_kind()` — если добавляешь
  новые сравнения с именами файлов/папок на macOS, помни про эту нормализацию.
- **Один и тот же код может встречаться в нескольких паспортах — по двум разным причинам,
  и их нельзя путать:**
  1. *Дубликаты одного проекта* — версии/копии (`old/`, `!old/`, `не актуальное/`,
     "conflicted copy", свежая пустая копия при передаче проекта другому РП — см. ниже).
     Тут нужно выбрать ОДИН файл, не суммировать.
  2. *Разные под-проекты под общим кодом* — например "Лукойл ПТП" и "Лукойл. Тираж 2"
     сидят на одном коде `FINO-032`, это два реальных разных паспорта, и Сводный
     суммирует их (см. `group_summary` — по той же причине один код может относиться
     к нескольким строкам-проектам). Тут значения из паспортов НУЖНО сложить, иначе
     получится расхождение на десятки миллионов на ровном месте.

  `select_passport()` различает эти два случая по имени "ПРОЕКТ" **внутри самого файла**
  (ячейка на листе "3. Договоры_Этапы_Доходы", читается в `read_passport_code_and_project()`):
  файлы с одинаковым (нормализованным) названием проекта — дубликаты, из них выбирается
  один; файлы с разным названием — разные под-проекты, их выбранные значения складываются.
  Кандидаты для этого берутся **из обеих групп сразу** — и "действующие", и "завершённые" —
  а не только из той, что соответствует статусу проекта в Сводном: у одного кода бывает
  несколько по-настоящему разных под-проектов, не обязательно все в одной группе.
  Пример — `FINO-009` (по этому коду попросил проверить пользователь): три реальных паспорта
  — два в "Действующих" у разных РП и один в "Завершённых" — и Сводный суммирует все три;
  раньше скрипт искал только в одной группе (по статусу) и терял часть суммы.

  Это эвристика по имени, а не гарантия: если проект в течение года переименовали, вместо
  дубликата можно ошибочно получить "два под-проекта" и лишний плюс к сумме (наблюдалось на
  `FINO-028`: "Фармасинтез" и "Фармасинтез_ТП" — по всей видимости один и тот же проект,
  черновая и финальная версия паспорта с разным названием внутри, но скрипт просуммировал
  их как два — небольшое ложное расхождение, ~250 тыс.). Обратной ошибки (два реальных
  под-проекта, которые скрипт принял за дубликат и потерял один) тоже нельзя полностью
  исключить, если оба носят одинаковое название "ПРОЕКТ". Скрипт всегда пишет warning вида
  "код делят N разных под-проекта (...) — суммированы" — при подозрении на завышенное
  расхождение из-за суммирования в первую очередь смотри эти строки в выводе, не саму логику.

  Внутри бакета (одинаковое название проекта) выбирается файл с **ненулевым** фактом за
  нужное полугодие, и только среди таких — самый свежий по дате изменения (не просто
  "самый свежий по mtime вообще"): при передаче проекта другому РП в его папке иногда
  создают свежую копию паспорта, которая ещё не заполнена (факт = 0), пока старая копия у
  прежнего РП всё ещё содержит реальные данные за прошедшие месяцы. Голый mtime в этом
  случае выбрал бы пустышку (было замечено на нескольких кодах в FinOps при передаче
  проектов между Нешковой/Черненко и Ливановой/Мертиняном).
- **В листе "4. Факт БДР" паспорта строка "1е полугодие" повторяется для каждого года**
  проекта (2025, 2026, 2027 — под каждым годом свой блок с той же меткой). Нельзя брать
  первое совпадение по тексту — обязательно сначала найти блок нужного года (`year` из
  конфига), и искать "1е полугодие" только после него, до начала следующего года
  (`read_passport_h1_actual()`).
- **Выгрузка из бухгалтерии — это pivot-таблица со "схлопнутыми" повторами на двух
  уровнях вложенности**: колонки "Код проекта"/"Проект" заполнены только в первой строке
  своей группы кода, а "Вид выручки" — только в первой строке своей подгруппы внутри
  кода (несколько договоров одного вида выручки идут подряд с пустой колонкой C).
  Все три поля нужно "протаскивать" вниз (`current_code_raw`/`current_proekt`/
  `current_vid` в `parse_revenue_extract()`), а не читать как есть — иначе часть строк
  в "Детали выручки"/"Осиротевшие коды" будет с пустым видом выручки, хотя реальные
  данные там есть, просто в ячейке выше. Из-за пустых ячеек в середине строки нельзя
  читать по порядку непустых — надо строго по атрибуту `r="C304"` (`xlsx_min.py`,
  `Workbook.read_sheet()` уже это учитывает). Итоговая сумма по коду — отдельная строка
  `"<КОД> Итог"` в конце группы, колонка "Общий итог" (последняя).
- **Нет доступа в интернет** в среде выполнения — `pip install`/`uv run --with X` не
  работают (проверено, proxy 403 на pypi.org). Любые доработки должны обходиться
  стандартной библиотекой Python 3.9 (та версия, что стоит в `/usr/bin/python3`).

## Если пользователь просит "сделай то же самое для другого направления/периода"

1. Спроси/уточни (или найди сам через `find`/чтение файла), как называется направление
   в Сводном, актуальный файл выгрузки за нужный период и лист года.
2. Поправь `config.json` (можно скопировать в `config_<направление>_<период>.json` и
   передать через `--config`, если нужно держать несколько конфигов параллельно).
3. Прогони `python3 sverka.py --config ...` и проверь предупреждения в конце — они
   обычно указывают на реальные проблемы с данными (коллизии кодов, нечитаемые файлы),
   а не на баги скрипта.
4. Перед тем как доверять цифрам — выборочно сверь 1-2 строки вручную (открыть Сводный
   и соответствующий паспорт), как это делалось при первой отладке. Расхождения типа
   "паспорт даёт 0, а везде большие цифры" почти всегда означают баг в чтении паспорта
   (например, взяли не тот год/полугодие), а не реальный ноль — перепроверяй.
